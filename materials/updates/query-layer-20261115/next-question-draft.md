# 下一步候选问题：自然更新中的无关事实保持

此页是讨论草稿。当前单层实验仍在运行；本页没有读取其部分科学结果，没有生成新事件流、登记下一轮运行包或执行额外模型推理。下一轮条件应在完整结果分析和备份之后正式登记。

已有完整证据来自前一轮 fresh-query Release：正常 GDN 适配器 Full 为 191/192，新值 32/32；人为恢复旧递归矩阵使新值降到 2/32，换入正常问题 Query 恢复到 32/32，同时有一条旧事实回答退化。它说明该交叉状态的读取可以被问题 Query 改变，尚未证明正常模型需要新的共享更新结构。

当前受控输入最长历史为 1,107 Token（211 前缀＋896 尾部），只有八条事件流、三个问题角色和 SET 操作。不能把这些结果当作长至 100K、自然语言复杂依赖或新架构收益的证据。

## 需要补上的问题

正常编码同一批目标事实后，在不人工恢复矩阵、不关闭更新门控的情况下，语义上独立的更新是否会稳定损害目标或保护对象的读出？这种现象是否在已有 GDN 强基线上仍出现，而非仅发生在较弱原生模型或人为交叉缓存上？

在已有模型近乎达到上限的任务上继续增加模块，不足以说明架构必要性。下一步优先寻找可复现的自然条件差异，同时保留相关更新必须正确生效的对照。

## 候选受控设计

保持相同正常前缀、相同目标/保护问题与真值，改变无关尾部的活跃实体数量；在相同记录数和 Token 预算下，比较少量实体反复更新与更多实体更新。增加较长尾部，区分长度和活跃事实负载。重复写入相同版本事实可作为后续独立对照，不能将其与 ADD 的累加语义混同。

新实体命名需要统一形式、分词长度控制与跨流重命名对照；否则实体词形、罕见标识符或模板外输入本身可能解释退化。保留原目标和保护对象的命名，以便检查新尾部域变化是否已经破坏短上下文能力。长度匹配不能证明所有分布混淆都被消除。

所有输入可行性检查应只依赖解释器真值和本地 Tokenizer；先登记规则，再生成和封存。保留接尾部前的全部错误，不按模型正确性筛选流。相关尾部应要求更新新值，并同时询问历史及保护对象，避免把不再更新当作保持能力。

先用固定原生模型与现有 GDN 检查点，不新增训练或环境。Full 负责实际任务表现；真实支持标注的 Oracle 只用于分开阅读竞争和条件可读性，不作为可部署 Router。只有已知问题可以用于参考激活捕获，Oracle 激活不能进入 Full 条件。

更长前缀的 eager 注意力可能需要分块 prefill；若采用，必须另行登记计算路径和运行控制，明确 BF16 全段与分块路径未必数值相同。不能借此修改当前封存源码、既有容差或已完成结果。

## 分析与决定

报告相同 Token 预算下的全部条件，分别列出当前更新、历史和无关事实保持；同时看自由回答、NLL 和逐流增益/退化。只有八条流时保持描述性解释，不把重复问题算成独立样本。

若自然条件下已有 GDN 基线仍稳定完成任务，应记录这一结果并重新选择研究对象。若存在稳定差异，再定位问题 Query、递归更新及证据访问各自的作用。单层移植成功只限定特定干预；它不能替代一个无需供体参考前向、能在正常部署中工作的改进方法。

新控制器、共享语义接口或更大模型训练需要由这些证据支持。所有原先失败判据维持原判；本草稿不增加新的架构成功门槛或扩模触发条件。
